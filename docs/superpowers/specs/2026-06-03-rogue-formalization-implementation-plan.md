## 3. 总体实施顺序
严格按以下顺序推进：
1. 职业核心系统
2. 通用构筑池
3. 战斗验证场
4. 局外成长框架
5. 统一包装与平衡

原因：
- 先建立职业身份，后扩构筑内容，避免系统发散
- 先建立构筑池，再引入 Boss/精英，确保验证对象成立
- 先把局内结构做稳，再接入局外成长，避免局外系统反向驱动设计

## 4. 迭代 1 实施计划：职业核心重构
### 4.1 开发目标
让战士、游侠、法师在开局阶段就具备明确不同的资源循环和构筑方向。

### 4.2 代码改动范围
- `src/game/types.ts`
  - 新增职业资源状态类型
  - 为 `PlayerState` 或 `RunState` 增加职业核心相关字段
- `src/game/content.ts`
  - 增加职业专属核心配置
  - 增加职业专属升级项配置
- `src/game/engine.ts`
  - 实现怒焰值、猎印、法印矩阵的累计与消耗逻辑
  - 将职业专属升级项并入升级池生成逻辑
  - 将职业资源与现有技能/元素系统联动
- `src/components/run/RunHud.tsx`
  - 新增职业资源显示区
- `src/components/run/CanvasArena.tsx`
  - 为职业核心增加最小可辨识视觉反馈

### 4.3 必做任务
- 战士实现怒焰累计、怒焰阈值收益与爆发反馈
- 游侠实现猎印叠层、引爆与高价值目标反馈
- 法师实现法印记录、基础组合和可见提示
- 升级池支持职业专属升级项
- HUD 明确显示职业资源状态

### 4.4 验收标准
- 玩家进入战斗后 30 秒内能感知职业差异
- 不同职业的强化项不再只是共用数值项
- 职业资源在 HUD 和战场上都可感知

### 4.5 测试要求
- 为每个职业核心至少补 1 条逻辑测试
- 验证升级池能包含职业专属强化
- 浏览器手动验证 3 职业起手差异

## 5. 迭代 2 实施计划：通用构筑池扩展
### 5.1 开发目标
建立可扩展的共享构筑池，让同一职业也能多次开出不同流派。

### 5.2 代码改动范围
- `src/game/content.ts`
  - 增加通用主动技能配置
  - 增加被动/词缀配置
  - 增加遗物配置
  - 增加元素反应配置
- `src/game/types.ts`
  - 增加遗物、被动词缀、元素反应相关类型
- `src/game/engine.ts`
  - 接入通用主动技能释放逻辑
  - 接入被动和遗物的效果处理器
  - 把元素附魔升级为元素反应结算
- `src/components/run/UpgradePanel.tsx`
  - 支持显示更多升级类别
- `src/components/run/RunHud.tsx`
  - 支持展示遗物和主要被动状态

### 5.3 必做任务
- 增加 6-8 个通用主动技能
- 增加 12-16 个被动/词缀
- 增加 10-14 个遗物
- 实现首批稳定元素反应组合
- 确保遗物能形成中局构筑转折

### 5.4 验收标准
- 同一职业至少能形成 2-3 种明显不同流派
- 中局能出现“拿到某个遗物后构筑方向改变”的体验
- 元素从附魔升级为可识别的组合玩法

### 5.5 测试要求
- 为元素反应与遗物结算补逻辑测试
- 为升级池分类补测试
- 手动验证至少 3 套不同构筑路线

## 7. 迭代 4 实施计划：局外成长框架
### 7.1 开发目标
建立长期推进目标，让玩家每局结束后有明确的解锁动机。

### 7.2 代码改动范围
- `src/store/`
  - 增加局外存档状态
- `src/pages/`
  - 新增局外成长页或营地页
- `src/game/types.ts`
  - 增加解锁、常驻成长、局外货币类型
- `src/game/content.ts`
  - 增加职业解锁树、构筑池解锁表、常驻成长节点配置
- `src/game/engine.ts`
  - 结算时输出局外奖励
- 新增本地持久化逻辑

### 7.3 必做任务
- 增加角色解锁界面
- 增加构筑池解锁入口
- 增加轻量常驻成长节点

### 7.4 验收标准
- 玩家打完一局后知道下一步解锁目标

### 7.5 测试要求

## 9. 横向工程要求
每次迭代都必须遵守以下工程要求：
- 优先扩展现有模块，不新增无边界的大文件
- 配置数据优先放在 `content.ts` 或后续拆分的数据目录中
- 新机制优先用类型系统和配置驱动描述
- 每轮结束必须运行：
  - `npm run check`
  - `npm run lint`
  - `npm test`
- 有明显新增逻辑时必须补对应测试

## 10. 每轮交付物
每次迭代结束后至少产出：
- 可运行代码
- 通过检查与测试
- 一轮浏览器试玩验证
- 简短变更说明
- 下一轮前置风险说明
