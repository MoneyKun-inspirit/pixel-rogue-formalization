# 迭代 2 实现计划：元素反应系统首版

## 1. 目标
基于已确认的元素反应规格，在当前 Demo 中落地“4 种稳定反应 + 先挂后触发 + 顺序有意义”的首版实现。

本轮实现目标不是构建完整元素生态，而是优先打通以下闭环：
- 敌人能够正确挂载主元素状态
- 第二元素命中时能按固定反应表触发反应
- 反应会正确消费旧状态并施加后续效果
- 玩家能从战场像素反馈中明确看出不同反应

## 2. 实现范围
### 2.1 本轮实现
- 增加元素挂载状态与反应类型
- 在内容配置中加入 4 种反应定义
- 在伤害/命中流程中接入统一反应判定
- 实现 4 种反应的伤害、范围和 debuff 结算
- 为 4 种反应加入最小必要的像素反馈
- 补充元素反应相关自动化测试

### 2.2 本轮暂不实现
- 三元素连锁
- 多元素长期共存
- 敌人抗性/元素克制
- 复杂反应教学面板
- 章节或 Boss 专属反应机制

## 3. 实施顺序
### 阶段 1：补齐类型与配置
目标：建立元素挂载与反应表的数据骨架。

改动：
- `src/game/types.ts`
  - 新增 `ReactionId`
  - 新增 `ReactionDefinition`
  - 新增 `ElementState`
  - 扩展敌人 `status`，加入 `elementState` 和 `meltedTimer`
- `src/game/content.ts`
  - 新增 `reactionTable`
  - 定义 4 种反应的名称、倍率、范围、消耗规则和后续状态

完成标准：
- 类型层能表达主元素挂载、反应定义和短时破口 debuff
- 初始敌人状态具备反应所需字段

### 阶段 2：打通单体挂载与统一判定
目标：让每次元素命中都能先查反应，再决定是否刷新挂载。

改动：
- `src/game/engine.ts`
  - 拆分现有 `applyElementStatus()` 逻辑
  - 新增 `applyElementBaseStatus(run, enemy, element)`
  - 新增 `tryTriggerReaction(run, enemy, triggerElement, damage)`
  - 新增 `triggerReactionEffect(run, enemy, reaction, damage)`

实现重点：
- 先判断是否触发反应，再决定是否刷新挂载
- 利用 `reactionLockTimer` 防止同一帧重复触发
- 保持现有火焰/寒冰/雷电基础状态不被破坏

完成标准：
- 同一个敌人能稳定挂载火或冰
- 第二元素命中时能正确查询反应表

### 阶段 3：实现 4 种反应结算
目标：让 4 种反应在伤害、范围和后续状态上都真正可用。

需要实现：
- `余烬 + 雷电 = 超载爆裂`
  - 小范围爆炸伤害
- `余烬 + 寒潮 = 蒸汽震荡`
  - 范围伤害 + 短减速
- `寒潮 + 雷电 = 导电碎裂`
  - 2-3 条额外电弧
- `寒潮 + 余烬 = 熔蚀穿透`
  - 转化为短时 `melted` 窗口，提高后续承伤

实现重点：
- 超载与蒸汽偏范围
- 导电偏连锁
- 熔蚀偏单体破口
- 所有反应都必须消费旧状态或转化状态

完成标准：
- 4 种反应都能在运行时被触发并产生不同结果

### 阶段 4：接入像素反馈
目标：让玩家一眼看出刚刚发生的是反应，而不是普通元素命中。

改动：
- `src/components/run/CanvasArena.tsx`
  - 超载爆裂：红黄闪爆 + 扩散圆环
  - 蒸汽震荡：白灰蒸汽波 + 冰蓝边缘
  - 导电碎裂：冰碎片 + 链状电弧
  - 熔蚀穿透：敌人外框裂纹或熔蚀边框

可复用现有：
- `attackEffects`
- `elementPalette`
- 现有 lightning / burst / nova 渲染语言

完成标准：
- 4 种反应的主轮廓能被明确区分

### 阶段 5：补测试与回归验证
目标：为元素反应建立最小可靠保护网，并确认遗物系统没有被带坏。

改动：
- `src/game/engine.test.ts`
  - 测试火后雷触发超载爆裂
  - 测试火后冰触发蒸汽震荡
  - 测试冰后雷触发导电碎裂
  - 测试冰后火触发熔蚀穿透
  - 测试反应消费/转化状态
  - 测试短时锁不会无限重复反应
- 运行：
  - `npm run check`
  - `npm run lint`
  - `npm test`
  - `npm run build`
- 浏览器试玩：
  - 抽查至少两个职业的反应构筑
  - 验证技能/词缀/遗物和元素反应的承接关系

完成标准：
- 检查、测试和构建全部通过
- 试玩中能看出元素反应确实成为终局构筑层

## 4. 关键实现决策
### 4.1 状态层最小扩展
不推翻现有 `burnTimer / slowTimer / shockTimer`。

策略：
- 保留原有基础状态计时器
- 额外增加 `elementState` 作为统一反应判定层
- 对熔蚀单独加 `meltedTimer`

原因：
- 最容易兼容当前已有的元素附魔和基础状态逻辑
- 风险明显小于整套状态系统重写

### 4.2 反应表驱动
不让每个技能自己决定如何反应。

策略：
- 在 `content.ts` 放统一反应表
- 在 `engine.ts` 统一查询和结算

原因：
- 当前技能数量已经上升，若把反应分散到技能分支里，复杂度会迅速失控
- 表驱动也更容易补测试

### 4.3 顺序保留
明确保留：
- 火后冰
- 冰后火

为两个不同结果。

原因：
- 让出手顺序和技能编排真正有构筑意义
- 也是这一版元素反应最值得保留的特色

## 5. 风险控制
- 如果 `engine.ts` 复杂度升高过快，优先把反应检测与执行提炼为独立函数
- 如果视觉表现时间不够，优先保证 4 种反应轮廓不同，而不是追求复杂粒子数量
- 如果导电碎裂与现有雷电连锁重叠过多，优先通过额外 attack effect 拉开视觉区别
- 如果熔蚀穿透对单体伤害影响过大，先限制持续时间而不是取消机制

## 6. 验收清单
- 敌人能稳定挂载主元素
- 第二元素命中时能按表触发正确反应
- 反应触发后旧状态会被正确消费或转化
- 4 种反应都有可辨识的像素反馈
- 自动化测试、类型检查、lint 和 build 全部通过
- 至少 2 个职业能围绕不同反应形成不同终局方向
